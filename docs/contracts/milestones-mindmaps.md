# Contract: milestones and mind maps

**Mandatory rules, with the same authority as `AGENTS.md`.** Read this file before changing
anything it covers: milestone status and lateness (`slips`, `unreachedOn`), Procedural mind maps (no SIR, `stageOf`, `liveSessions`, `targetFor`, the Kolb reset), a mind map's `strat`, and SRCH → DIRECTORY (`parentIds` moves).

Moved out of `AGENTS.md` on 2026-11-10, word for word and with nothing deleted, because
`AGENTS.md` had reached 174KB and is loaded into every agent session. A phrase such as
"the `merges` rule" or "the `time` / `link` rule" names a rule in this file or a sibling
one; the index in `AGENTS.md` ("Feature contracts") says which file holds which key.
A new rule for this area is added HERE, not to `AGENTS.md`.

---

A milestone is **overdue** when its end has passed and its work — the tasks under its blocks, and each `toLearn` mind map's waypoint for it — is not all done. `scripts/milestone-core.js` (`window.TrackMilestone`) is the one definition, and four surfaces draw it: the Milestones tab (row and calendar), the Home and Documentations month tails through `calendar-core.js`, and the Schedule's ⚑ rows and pickers. Seven rules follow, and the first two are the load-bearing ones:

- **One definition, and the six `progress.html` names are DELEGATES.** `countProgress`, `isMMTargetMet`, `buildSirDoneMap`, `STAGE_ORDER`, `collectMilestoneOwners` and `collectMilestoneBlocks` stay in the page only so their call sites do not move. Never re-inline one: Home cannot read `progress.html`, so a page-local copy is how the Milestones tab and the calendar tails would come to disagree about "done" — the deadline-caution shape again. `tests/milestone-core.test.js` pins the module against **verbatim copies** of the pre-extraction functions; the two deliberate differences (a link cycle terminates, a block reached twice counts once) have cases of their own.
- **Iterate `toLearn`, never `Object.entries(mmTargets)`.** Those keys are strings and mind-map ids are NUMBERS, so a key-driven loop compares `'10'` with `10` and silently finds nothing — `computeMMAutoComplete` already does exactly that (NOTES). A waypoint is judged ALONE: `targetMet(mm, waypoint, sirDone)`, the call the MM bar makes.
- **The end day is not late, and an EMPTY milestone never is.** Lateness starts the day after `endDate`; no tasks and no waypoints is `empty`, not overdue, at any date (the user's rule: nothing to chase). Missing, malformed or inverted dates are `undated`. The first two each have browser guards and doctored baselines in both suites; `undated` is pinned offline.
- **"Today" is a PARAMETER, and `opts.today` is opt-in.** The module holds no `Date` (day differences are integer days-from-civil), so its suite is unswept. `TrackCalendar.buildMilestoneLanes` draws a tail only when a caller passes `opts.today` AND the module is loaded; without either its output is byte-identical, and an on-time segment never gains a key. `drawEnd` is the one definition of the drawn span — today while late — and both `calendar-core.js` and the Milestones tab's calendar draw `[startDate, drawEnd]`.
- **Every walker in the module is cycle-guarded.** The "link existing task" picker offers a task's ancestors, so a link cycle is reachable through ordinary use, and Home and Documentations now follow links through this module. A per-path guard where a diamond must still count twice (`countLeaves`), visited-at-enqueue elsewhere.
- **What a day still owes its milestone has ONE definition, `TrackMilestone.unreachedOn(rep, mms, day, today)`**, read by the Schedule's ● Learn strip and Progress → MG — two surfaces of one page, which is exactly how a rule comes to be spelled twice. The milestone a day belongs to is the one whose dates COVER it (the user's rule since 2026-07-18), plus any already overdue; membership is `st.learn.open`, so "reached?" is `targetMet` and nothing re-asks it — a level EQUAL to the waypoint is reached. The **from-today gate lives inside it**: a past day pins nothing on either surface. Never re-spell the covering test, the overdue branch or the gate at a call site. The page splits its records by `procedural`: a Procedural MM is pinned by its MG (toggling `mgSchedule`), anything else as a mind map to study (adding `mmEntries`) — the user's T1/T2 split, so a Procedural MM on a late milestone is no longer pinned as a mind map.
- **`slips` has ONE writer, `TrackMilestone.withSlip`, called only from `updateMilestonePeriod`.** A milestone definition may carry `slips: [{from, to?, on}]`, all local days: absent when there are none, `[]` never written, `to` absent when the dates were cleared. It records only a move that pushes an ALREADY-LATE milestone's end later or clears it — the baseline is the state the edit STARTED from (captured on a date input's focus, else read from the tree before the write) — and it is the net effect of one day's edits from one due day: same `(on, from)` updates `to`, a move back removes the record and the key. It rides every writer that touches a definition by spread or move, and goes only with the definition itself. Not validated in `schema.js`; `slipsOf` is the total reader.
- **Milestone date inputs commit only a COMPLETE day inside `[MILESTONE_CAL_START, MILESTONE_CAL_END]`, never `''`** — `MilestoneDateInput` in `progress.html`, through `TrackGoals.isMilestoneDay`, moving the other bound through `TrackGoals.periodWithDay`. Never spell either test at an input again. Documentations' Projects tab had a twin until 2026-10-29, when the user asked for no date fields on the goal page; a date field added back anywhere goes through the same two functions. Chrome's year segment passes through `0002`, `0020` and `0202`; committing those collapsed the period on every keystroke and would now write slips no UI can delete. Emptying a field by keyboard is therefore not a way to clear dates — the confirm-gated `clear` button is, and its message names the slip when the milestone is late.

**A Procedural mind map (stored type `'2'`) has no SIR** (docs/CONCEPTS.md). `TrackMilestone.stageOf`, `liveSessions` and `targetFor` are the one definition, and four pages read them: `sir-ks02.html`, `progress.html`, and `index.html` / `documentations.html` through `calendar-core.js`. Seven rules follow, and the first two are the load-bearing ones:

- **DRAW a phase through `stageOf`, never from `mm.ksStage`.** A Procedural MM stored in SIR or FINISHED reads as S4; only writers read the stored value. `sir-ks02.html` and `progress.html` each hold a one-line `stageOf` delegate. A raw `ksStage` read at one surface is the deadline-caution failure shape again.
- **Filter what is DRAWN, never the `sessions` STATE.** `liveSessions` feeds KS02's `sessionsByDate` / `sirSessionsMap` memos and Progress's `sessions` prop; KS02's autosave writes the raw `sessions` state back, so filtering it there would delete the very sessions switching back to Declarative must restore. Progress never writes `sessions` at all, which is why it can filter at its root. The Schedule's ● Learn strip reads sessions FRESH (`_readSessions()`) for its SIR DUE group, so it calls `liveSessions` itself — the `◎` picker it replaced did not, and listed a Procedural MM's hidden session as due.
- **Nothing stored changes on read.** Switching a Procedural MM back to Declarative restores SIR and every session; the type switch rewrites no `ksStage`.
- **Every move out of SIR that deletes sessions asks first — Procedural or Declarative.** `saveLinSession` moving an MM out of a STORED SIR/FINISHED state deletes its sessions (leaving SIR always has), so it `window.confirm`s before any write and returns `false` on Cancel; the writer decides deletion by the STORED stage (`fromStage`), not by the option's `oldValue`, which is the phase the user saw. `endingSirSessions(mm, newStage)` is the prompt's copy of that same condition — keep the two identical, or the prompt and the delete disagree. A Procedural MM gets the "hidden sessions" wording, a Declarative one a count with how many are done. A move with no sessions to delete does not ask.
- **Every SIR entry point refuses a Procedural MM** — the `+LIN` option, `saveLinSession` (at the writer too), `duplicateMM` and `addMM`.
- **A Procedural MM's target is its level alone, read through `TrackMilestone.targetFor`** — the phase stripped from the target and every waypoint, and a waypoint left with no level dropped, so a phase-only target is NO target rather than a met one. `targetMet` and `statusOf` apply it; `progress.html` has eight "does this MM have a target?" readers and each calls its `targetOf` delegate, with a browser case and a doctored baseline per site. **Never hand `targetOf`'s result to a writer**: `setTarget`, `addMilestoneEntry`, `updateMilestoneEntry` and `removeMilestoneEntry` re-read the raw `mmTargets`, which is what keeps a stored phase target, unread, for the day the MM is switched back.
- **A Kolb ARRIVING on a Procedural MM resets it to S1, through `TrackKolb.resetPlan` / `withReset` and nowhere else** (KS02's `kolbResetPlan` is a delegate that adds the prompt). It arrives four ways: `saveKolb` (SAVE and the timer), the KOLB tab's edit `onSave` when the Kolb's `mmId` changes to a different MM, from none included, and in the notes widget a draft's `Done` and a Kolb's mind-map choice. Every one asks BEFORE any write; KS02's two return `false` on Cancel; the edit view keeps itself marked unsaved on `false`. The reset logs a `kolbReset` LIN change (`oldValue` the phase SHOWN, plus `kolbId`) that `computeLinActiveDays` must keep excluding, exactly like `stageRevert` — a new LIN change type is counted toward the streak unless it is excluded there. `duplicateKolb`, and an edit that leaves the Kolb on its MM, must not reset: both were the user's decisions.

A mind map may carry `strat`, its one **STRAT** (strategy): `{text, createdAt, updatedAt, originId?}`, times in epoch ms. It is an item-level key inside `mms`, so it adds **no** slot field and nothing was migrated. `scripts/strat-core.js` (`window.TrackStrat`) is the one definition; `sir-ks02.html` authors it (the user's 2026-10-25 request) and `progress.html` reads it. Nine rules follow, and the first three are the load-bearing ones:

- **One per mind map BY CONSTRUCTION: a single key, never a list.** That is the user's "one original". A list capped at one would be a rule every writer had to remember; a key has no second place to write into. The KS02 panel offers its add box only while `stratText` is empty, because `+` beside an existing original would silently overwrite it.
- **A STRAT may SPREAD FROM a mind map above its writer — `originId`, the user's 2026-11-10 rule — and then from that ORIGIN ALONE.** The origin and everything under it show it; the writer's own descendants see it only because they are under the origin too. It takes the origin's one STRAT, so the one-per-mind-map rule now has a SECOND door that construction cannot close, and the WRITER is its guard: `withStratOrigin` refuses whatever `TrackStrat.linkRefusal` refuses (not above, the origin has its own STRAT, another STRAT already spreads from it), and `withStrat` refuses to CREATE a STRAT on a mind map one spreads from. `linkRefusal` is the one test — the `↑ spread from…` picker greys a row by it (`aria-disabled`, never `disabled`) and the row still calls the writer, never re-checks; a doctored `withStratOrigin` that skips it fails exactly the greyed-row case. The link is ONE hop (an origin's own link is never followed, so no chain can loop) and is READ, never repaired: a writer moved out from under its origin keeps spreading from it (the user's choice), and an origin that is gone, or is the writer, reads as no link with the key kept. `stratsFor` always lists the mind map's own STRAT, wherever it spreads from, so a moved writer can still edit, unlink and delete it.
- **Inherited by EVERY descendant, read through `TrackStrat.stratsFor` and nowhere else** — farthest ancestor first, the mind map's own last, breadth-first with visited-at-enqueue, ids in a `Map` (a mind-map id is a NUMBER, and an object key would make `10` and `'10'` one id). Two surfaces read it, KS02's `StratSection` and the Schedule's ◎ STRAT button and panel; never walk `parentIds` for a STRAT at a call site, and never gate the button on the mind map's OWN STRAT — a block whose STRATs are all inherited must still show it. A doctored baseline gating it so fails exactly that case. A child holds no copy, so an edit or delete reaches every descendant at once.
- **`withStrat` REFUSES blank text** and returns its input when the text is already so; **`withoutStrat` deletes the KEY**, never `''` or `null`. A save is therefore never a delete: SAVE is disabled on blank text, and `removeStrat`'s `window.confirm` is the only door, in the handler and before the `setMms` the autosave writes from.
- **`originId` is absent by default and unlinking DELETES the key, never `null`** (`withoutStratOrigin`); linking writes `originId` and nothing else — not `updatedAt`, since a link is not an edit of the words — so unlink-then-link restores the record exactly. Linking deletes nothing and asks nothing; **unlinking asks** (the user's choice), in `unlinkStrat` before its `setMms`, and `removeStrat`'s prompt names the origin when there is one.
- **Read-only outside the mind map that owns it** (the user's choice): a child draws its ancestors' STRATs with no `✎` and no `×`, the origin draws a STRAT spreading from it as `FROM <writer>` with neither, and Progress only reads — `mms` is KS02's key.
- **Every mind-map name on a STRAT is a link** (the user's choice, 2026-11-10): in KS02 it opens that mind map in place through `onNavigate`, on INFO for an anchor and KS03 otherwise; on the Schedule it is `sir-ks02.html?mm=<id>`. That works only because **every `<MMDetail>` is keyed by mind map and opens on `selectedMMMode`**, which `openMM` sets in the same step. Never unkey one: an unkeyed panel keeps the tab it was on, and an anchor shown on KS03 draws nothing — a doctored ks03-view panel without its key fails exactly the case that opens an anchor from a STRAT link.
- **The times are `Date.now()` passed in as `now`**, never `today()`, which is this page's UTC-day helper. That is what keeps `strat-core.js` free of date code and its suite unswept, and a structural case greps the module, comments stripped, to prove it.
- **Not validated in `schema.js`**, like every other mind-map key: it is read only through `stratText`, which accepts any value and cannot throw.

**SRCH → DIRECTORY** (`sir-ks02.html`'s `MMDirectoryView`, the user's 2026-11-03 request) draws every mind map as a tree beside a page per mind map, and moves children by a held drag — a reorder between blocks, a nest onto a tree row, a move to Top level, one block or a ticked group. It adds **no** key: a move rewrites `parentIds` and the order of `mms`, nothing else. `scripts/mm-tree-core.js` (`window.TrackMMTree`) is the one definition. Eight rules follow, and the first three are the load-bearing ones:

- **`withNested`, `withArranged` and their composition `withPlaced` are the only writers, and the writer is the guard.** A nest is a MOVE: the child drops `fromId` (the page or drawn parent it was dragged from), the target takes that parent's PLACE in `parentIds`, any other parent stays, and the order of `mms` is never touched by `withNested` — only `withArranged` reorders, so colours by position (`mmColor`, NOTES Proposal 18) move only on a reorder. A move into the dragged mind map itself or its own branch is REFUSED by returning the very list, and the red row asks the SAME `moveRefusal` the writer does — never a page-local copy. All return their input when nothing changes. SRCH → LIST's reorder is a delegate to `withArranged`; never spell a `parentIds` transform at a call site.
- **A reorder is judged by the DRAWN list, never by stored indices.** The page passes `listId` (the open mind map), and `withArranged` returns its input for a drop that keeps the block's place in that list — which is also what hides the line (`hitAt` asks it). Without that, a drop back onto a block's own place rewrote `mms` whenever a mind map outside that list sat between it and its neighbour in the stored list, recolouring mind maps for a no-op. A doctored `withArranged` that ignores `listId` fails exactly the case that asserts no line and no write.
- **The drop reads the CURRENT `mms`, never the press's.** The engine reads `liveRef` at commit and App's `onNest` / `onArrange` are functional `setMms` updaters, so a rename another tab wrote mid-drag survives the move. This is a guard case, not a fail-first one: breaking it takes two edits, because either door alone still lands on the fresh list.
- **Ids come back from the DOM through `keyMap`, never `Number()`.** A `data-mmdir-*` hook is text and mind-map ids are numbers (`nid()`); `keyMap` maps `String(id)` to the id as stored, so a string id from a hand-edited file survives too. Fold state is keyed by `mmdirKey`, which keeps `10` and `'10'` apart.
- **The gesture engine binds its listeners AT THE PRESS**, not from an effect — an effect runs after a render and loses the moves that arrive first (the Documentations touch-drag lesson). The `touchmove` listener is non-passive and calls `preventDefault` only after the hold has lifted the block, so a finger that moves first still scrolls; a click after a drag is swallowed through `suppressClickUntil`, and a mouse press within 800ms of a touch is ignored.
- **Nothing that is drawn may move under a dragged block.** Top level takes the FILTER's place at the same height rather than being inserted above the rows (inserted, it shifted every row ~30px under the pointer), and over the tree the ghost shrinks to a chip beside the pointer so the row it is over stays visible. The ghost's width and transform are written by the engine alone (`placeGhost`, also run from a layout effect when the drag begins); React never sets either, because every re-render during a drag — each new hit is one — would put back the value it rendered over the one the engine just wrote.
- **A state rule in the DIRECTORY CSS is (0,4,0)** — `.mmdir [data-mmdir-list] .mmdir-block[data-mmdir-state="lifted"]`, `.mmdir .mmdir-bar .mmdir-row[data-mmdir-hit="nest"]`. Grit's Tailwind remaps are `html[data-theme="grit"] :is([class~="…"])`, (0,2,1), and their `:hover` forms (0,3,1), so a (0,3,0) drop highlight would lose to the hover remap under the very pointer that is dropping. The tick and the ticked block take their colours from tokens (`--color-primary-*`), not from indigo utilities in the JSX.
- **`MMDetail`'s `embedded`, `slotTop` and `slotBottom` are absent everywhere but DIRECTORY**, so every other surface draws the panel exactly as before; the trail and the CHILDREN list ride in those slots. No drag asks first — see the exemption list under "Confirm before deleting or clearing stored data".

Tree-row placement extends that same engine (2026-11-10):

- **`withPlaced(mms, id, fromId, parentId, targetId, before)` moves one occurrence and then
  arranges it.** `fromId` comes from that row's path, null at the top, never from the open page.
  Different parents compose `withNested` then `withArranged`; the same parent is a reorder
  (`moveRefusal`'s `same` is not an error). Every other refusal is unchanged. `targetId` is a
  sibling anchor, null for the end or an empty parent; a missing/foreign anchor aborts both
  steps. `withArranged` with `listId: null` judges the drawn `roots`, including cycle entries;
  a named parent judges its drawn children. Nothing drawn changing means the original input.
  Moving a multi-parent row to Top level still removes only `fromId`: it remains under its
  other parents, exactly as `withNested` did. App calls `withPlaced` through one functional
  `setMms` updater over the current list.
- **Only tree drags use tree insertion lines.** The edge zone is the smaller of 10px and a
  quarter of the row's height, at both ends; the middle keeps `data-mmdir-hit="nest"`. A gap
  below an open parent means its first child. Else, the following row's depth through the
  preceding row's depth are the possible levels (zero at the tree's ends); choose the closest
  14px indent to the pointer's x, measured from the row's left + 4px, clamped to that interval.
  The finite rendered-path scan ends where `MMDirRow`'s cycle guard ends. Refusals stay red and
  explained, and a writer-judged no-op has no line. The dot and 2px line are absolute
  pseudo-elements, not inserted rows. They never shift a target.
- **A tree drag lifts one path only.** Ticked groups remain a CHILDREN feature; other occurrences
  of the same mind map do not lift. `↻` repeated rows and rows while the filter contains any
  text do not lift. The 400ms hold, pre-hold scroll cancellation, ghost placement, hover-unfold
  and edge auto-scroll all remain in the existing engine. A short press opens, a drag's release
  cannot also click, and the caret does not start a drag. Paths return ids through `keyMap`'s
  typed map (separate from legacy block attribute keys), preserving numeric/string identities.
